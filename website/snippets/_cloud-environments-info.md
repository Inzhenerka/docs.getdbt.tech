## Типы окружений {#types-of-environments}

В <Constant name="dbt" /> есть два типа окружений:
- **Окружение развертывания** &mdash; Определяет настройки, используемые при выполнении заданий, созданных в этом окружении.<br></br>
    Типы окружений развертывания:
    - Общее (General)
    - Предпродакшен (Staging)
    - Продакшен (Production)
- **Окружение разработки** &mdash; Определяет настройки, используемые в <Constant name="studio_ide" /> или <Constant name="platform_cli" /> для конкретного проекта.

В каждом проекте <Constant name="dbt" /> может быть только одно окружение разработки, но при этом любое количество общих окружений развертывания (General), одно окружение развертывания для продакшена (Production) и одно окружение развертывания для предпродакшена (Staging).

|          | Разработка | Общее (General) | Продакшен (Production) | Предпродакшен (Staging) |
|----------|-------------|---------|------------|---------|
| **Для чего определяет настройки** | <Constant name="studio_ide" /> или <Constant name="platform_cli" /> | Запуски заданий <Constant name="dbt" /> | Запуски заданий <Constant name="dbt" /> | Запуски заданий <Constant name="dbt" /> |
| **Сколько таких окружений может быть в проекте?** | 1 | Любое количество | 1 | 1 |

:::note 
Для пользователей, знакомых с разработкой в <Constant name="core" />, каждое окружение примерно соответствует записи в файле `profiles.yml`, дополненной информацией о репозитории, которая обеспечивает выполнение нужной версии кода. Подробнее об окружениях v1 читайте [здесь](/docs/local/dbt-environments).
:::

### Поведение custom branch {#custom-branch-behavior}

По умолчанию все окружения используют основную ветку вашего репозитория (обычно ветку `main`) при доступе к вашему коду dbt. Это можно переопределить в каждом окружении <Constant name="dbt" /> с помощью параметра **Default to a custom branch**. Поведение этого параметра немного различается в зависимости от типа окружения:

- **Разработка**: определяет ветку, от которой разработчики создают ветки в <Constant name="studio_ide" /> или <Constant name="platform_cli" /> и в которую направляют PR.
- **Развертывание:** определяет ветку, которая клонируется при выполнении заданий в каждом окружении.

Подробнее см. на [FAQ‑странице по этой теме](/faqs/Environments/custom-branch-settings)!

### Расширенные атрибуты (Extended attributes) {#extended-attributes}

:::note 
Расширенные атрибуты сейчас _не_ поддерживаются для SSH‑туннелирования
:::

Расширенные атрибуты позволяют задать фрагмент [`profiles.yml`](/docs/local/profiles.yml), который изменяет способ подключения <Constant name="dbt" /> к вашей платформе данных. Вы можете задать любые YAML-атрибуты, которые адаптер dbt поддерживает в своем `profiles.yml`. Расширенные атрибуты частично переопределяют учетные данные подключения или среды, включая пользовательские переменные среды.

Место их настройки зависит от среды:

**Развертывание:** В [профиле подключения](/docs/platform/about-profiles), назначенном среде:

1. Перейдите в **Orchestration** > **Environments**.
2. Откройте среду развертывания и нажмите **Settings**.
3. Нажмите **Edit**.
4. В разделе **Connection profiles** нажмите на имя профиля.
5. Добавьте **Extended attributes** и сохраните изменения.

Один профиль может быть назначен нескольким средам развертывания, поэтому эти атрибуты применяются ко всем средам, которые его используют.

**Разработка:** [Профили](/docs/platform/about-profiles) применяются только к средам развертывания. Задайте **Extended attributes** на странице **Settings** среды разработки:

1. Перейдите в **Orchestration** > **Environments**.
2. Откройте среду разработки и нажмите **Settings**.
3. Нажмите **Edit profile**, затем задайте **Extended attributes** и сохраните изменения.

<Lightbox src="/img/docs/dbt-platform/using-dbt-platform/extended-attributes.png" width="95%" title="Поле Extended attributes в профиле подключения." /> <br />

Следующий код демонстрирует примеры типов атрибутов, которые можно добавить в текстовое поле **Extended attributes**:

```yaml
dbname: jaffle_shop      
schema: dbt_alice      
threads: 4
username: alice
password: '{{ env_var(''DBT_ENV_SECRET_PASSWORD'') }}'
```
#### Extended Attributes не маскируют значения секретов {#extended-attributes-dont-mask-secret-values}
Мы рекомендуем избегать указания секретных значений, чтобы они не были видны в текстовом поле и логах. Распространённый обходной путь — обернуть extended attributes в [environment variables](/docs/build/environment-variables). В примере выше `password: '{{ env_var(''DBT_ENV_SECRET_PASSWORD'') }}'` получит значение из переменной окружения `DBT_ENV_SECRET_PASSWORD` во время выполнения.

Вы также можете использовать массивы в качестве значений ключей. Например, чтобы передать список групп базы данных:

```yaml
db_groups:
  - db_editor
  - db_viewer
```

#### Расширенные атрибуты не скрывают секретные значения

- Рекомендуем не задавать секретные значения напрямую, чтобы они не отображались в текстовом поле и логах. Распространённый способ обойти это ограничение — использовать [переменные окружения](/docs/build/environment-variables) в расширенных атрибутах. В предыдущем примере `password: '{{ env_var(''DBT_ENV_SECRET_PASSWORD'') }}'` получит значение из переменной окружения `DBT_ENV_SECRET_PASSWORD` во время выполнения.
- Если вы используете [профили](/docs/platform/about-profiles) для окружений развёртывания, все ссылки `env_var` в расширенных атрибутах должны использовать переменные окружения, заданные _на уровне проекта_. Поскольку профили не привязаны к конкретному окружению, переменные уровня окружения недоступны во время проверки подключения. Задания выполняются нормально, поскольку у них есть конкретное окружение, но проверки подключения завершатся ошибкой, если переменная, на которую ссылается профиль, задана только на уровне окружения.

  Чтобы задать переменную на уровне проекта, перейдите в **Orchestration** > **Environments** > **Environment variables** и укажите значение в столбце **Project default**. Это значение применяется ко всем окружениям проекта, благодаря чему оно доступно профилям во время проверки подключения. Подробнее см. в разделе [Переменные окружения](/docs/build/environment-variables?version=2.0#setting-environment-variables).

#### Как работают расширенные атрибуты
Если вы разрабатываете в [<Constant name="studio_ide" />](/docs/platform/studio-ide/develop-in-studio), [<Constant name="platform_cli" />](/docs/platform/dbt-cli-installation) или [оркестрируете запуски заданий](/docs/deploy/deployments), механизм расширенных атрибутов разбирает предоставленный YAML и извлекает атрибуты `profiles.yml`. Для каждого отдельного атрибута:

- Если атрибут существует в другом источнике (например, в настройках проекта), его значение в профиле (например, значение уровня окружения) будет заменено. Он также переопределяет любые пользовательские переменные окружения (если сам не использует их через синтаксис, описанный выше для секретных значений)

- Если атрибут не существует, соответствующая пара «атрибут — значение» будет добавлена в профиль.

#### В расширенных атрибутах допускаются только **ключи верхнего уровня**
Это означает, что для изменения значения конкретного вложенного ключа необходимо указать весь ключ верхнего уровня в виде блока JSON в итоговом YAML. Например, если вы хотите настроить определённое поле в [JSON-файле сервисного аккаунта](/docs/local/connect-data-platform/bigquery-setup?version=1.12#service-account-json) для подключения к BigQuery (например, 'project_id' или 'client_email'), необходимо с помощью расширенных атрибутов переопределить целиком основной ключ/атрибут верхнего уровня `keyfile_json`. Включите вложенные поля в виде вложенного блока JSON.
