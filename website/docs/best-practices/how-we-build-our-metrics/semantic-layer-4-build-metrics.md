## Как создавать метрики

- 💹 Начнем с одной из самых важных метрик для любого бизнеса: **выручка**.
- 📖 На данный момент наша метрика для выручки будет **определена как сумма итогов заказов без учета налогов**.

## Определение выручки {#defining-revenue}

- 🔢 Метрики имеют четыре основных свойства:
  - `name:` Мы будем использовать 'revenue' для обозначения этой метрики.
  - `description:` Для документации.
  - `label:` Отображаемое имя метрики в последующих инструментах.
  - `type:` один из `simple`, `ratio` или `derived`.
- 🎛️ Каждый тип имеет разные `type_params`.
- 🛠️ Сначала мы создадим **простую метрику**, чтобы освоиться, а затем перейдем к метрикам типа ratio и derived.
- 📏 Простые метрики строятся на **одной мере, определенной как параметр типа**.
- 🔜 Определение **мер как их собственных отдельных компонентов** в семантических моделях критически важно для обеспечения **гибкости более сложных метрик**, хотя простые метрики в основном действуют как **передаточные, предоставляющие возможности фильтрации** и маркировки.

<File name="models/marts/orders.yml" />

```yml
metrics:
  - name: revenue
    description: Sum of the order total.
    label: Revenue
    type: simple
    type_params:
      measure: order_total
```

## Запрос вашей метрики {#query-your-metric}

Вы можете использовать <Constant name="platform_cli" /> для проверки метрик или выполнения запросов в процессе разработки с помощью набора подкоманд `dbt sl`. Вот несколько полезных примеров:

```bash
dbt sl query revenue --group-by metric_time__month
dbt sl list dimensions --metrics revenue # список всех доступных измерений для метрики выручки
```

- При каждом обновлении кода <Constant name="semantic_layer" /> рекомендуется запускать `dbt parse`, чтобы обновить семантический манифест среды разработки.
- `dbt sl query` — не тот способ, которым обычно пользуются этим инструментом в производственной среде: там за это отвечают возможности семантического слоя <Constant name="dbt" />. Эта команда предназначена для проверки результатов различных запросов к метрикам в среде разработки — именно так мы и используем её сейчас.
- Обратите внимание на структуру приведённого выше запроса. Мы выбираем нужные метрики и измерения, по которым их следует сгруппировать, — и используем двойные подчёркивания (dunders, например `metric_time__[time bucket]`) для обозначения временных измерений или других неуникальных измерений, для однозначного определения которых необходимо указать путь через сущность (например, если у вас есть измерение местоположения заказа и измерение местоположения сотрудника, оба с именем 'location', вам понадобятся двойные подчёркивания, чтобы указать `orders__location` или `employee__location`).
