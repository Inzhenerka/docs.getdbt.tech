`dbt compile` требует подключения к платформе данных для того, чтобы собрать необходимую информацию (включая данные из интроспективных запросов) для подготовки SQL для каждой модели в вашем проекте.

### dbt compile {#dbt-compile}

Команда [`dbt compile`](/reference/commands/compile) генерирует исполняемый SQL из файлов `source`, `model`, `test` и `analysis`. `dbt compile` похож на `dbt run`, за исключением того, что он не материализует скомпилированный SQL модели в существующую таблицу. Таким образом, до момента материализации, `dbt compile` и `dbt run` схожи, потому что оба требуют подключения к платформе данных, выполняют запросы и имеют переменную [`execute`](/reference/dbt-jinja-functions/execute), установленную в `True`.

Однако, стоит учитывать следующие моменты:

- Вам не нужно выполнять `dbt compile` перед `dbt run`
- В dbt, `compile` не означает `parse`. Это потому, что `parse` проверяет ваш написанный `YAML`, настроенные теги и так далее.

### Интроспективные запросы {#introspective-queries}

Для генерации скомпилированного SQL для многих моделей, dbt необходимо выполнять интроспективные запросы (когда dbt нужно выполнить SQL, чтобы получить данные и что-то с ними сделать) к платформе данных.

К таким запросам для анализа метаданных относятся:

- Заполнение кеша отношений. Подробнее см. в руководстве [Создание новых материализаций](/guides/create-new-materializations). Кеширование ускоряет проверки метаданных, в том числе проверку того, существует ли уже [инкрементальная модель](/docs/build/incremental-models) на платформе данных. 
- Выполнение [макросов](/docs/build/jinja-macros#macros), таких как `run_query` или `dbt_utils.get_column_values`, которые вы используете для формирования SQL по шаблонам. Это необходимо, поскольку dbt должен выполнять эти запросы во время компиляции SQL моделей. 
- [`dbt docs generate`](/reference/commands/cmd-docs) по умолчанию компилирует проект (если не передать [`--no-compile`](/reference/commands/cmd-docs)), поэтому макросы для анализа метаданных, такие как [`run_query`](/reference/dbt-jinja-functions/run_query), выполняются в хранилище данных при сборке документации так же, как и при других процессах компиляции. Подробнее о том, как это работает и как использовать `flags.WHICH`, чтобы ограничить выполнение <Term id="dml" /> или другого SQL с побочными эффектами определёнными командами dbt, см. в разделе [`run_query`](/reference/dbt-jinja-functions/run_query).

Без подключения к платформе данных dbt не может выполнять эти запросы для анализа метаданных и не сможет сгенерировать скомпилированный SQL, необходимый для следующих шагов рабочего процесса dbt. Без подключения к интернету или платформе данных вы можете выполнить [разбор проекта командой `parse`](/reference/commands/parse) и [получить список ресурсов проекта командой `list`](/reference/commands/list). Разбора проекта достаточно для создания [манифеста](/reference/artifacts/manifest-json), однако имейте в виду, что сохранённый манифест не будет содержать скомпилированный SQL.

Для настройки проекта вам необходим [профиль подключения](/docs/local/profiles.yml) (`profiles.yml`, если вы используете CLI). Этот файл нужен, поскольку конфигурация проекта зависит от его содержимого. Например, вам может потребоваться использовать [`{{target}}`](/reference/dbt-jinja-functions/target) для условных настроек или знать, с какой платформой вы работаете, чтобы выбрать подходящий диалект SQL.
