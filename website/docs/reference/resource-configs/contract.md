Когда конфигурация `contract` применяется в обязательном порядке, dbt гарантирует, что набор данных, возвращаемый вашей моделью, в точности соответствует атрибутам, определённым в YAML:
- `name` и `data_type` для каждого столбца
- Дополнительные [ограничения (`constraints`)](/reference/resource-properties/constraints), поддерживаемые данной материализацией и платформой данных

Когда конфигурация `contract` применяется, dbt будет гарантировать, что возвращаемый набор данных вашей модели точно соответствует атрибутам, которые вы определили в yaml:
- `name` и `data_type` для каждого столбца
- Дополнительные [`ограничения`](/reference/resource-properties/constraints), как поддерживается для этой материализации и платформы данных

Контракты позволяют управлять проверкой соблюдения схем — как для отдельной модели, так и единообразно для множества моделей в проекте.

Обратитесь к разделу [Примеры](/reference/resource-configs/contract#examples), чтобы узнать, как применять контракты в вашем проекте.

В настоящее время контракты моделей поддерживаются для:
- SQL моделей (пока не для Python)
- Моделей, материализованных как `table`, `view` и `incremental` (с `on_schema_change: append_new_columns` или `on_schema_change: fail`)
- Наиболее популярных платформ данных — хотя поддержка и применение различных [типов ограничений](/reference/resource-properties/constraints) варьируются в зависимости от платформы

## Алиасинг типов данных {#data-type-aliasing}

dbt использует встроенный алиасинг типов для `data_type`, определенного в вашем YAML. Например, вы можете указать `string` в вашем контракте, и на Postgres/Redshift dbt преобразует его в `text`. Если dbt не распознает имя `data_type` среди известных алиасов, он передаст его как есть. Это включено по умолчанию, но вы можете отказаться, установив `alias_types` в `false`.

Пример отключения:

<File name='FOLDER_NAME/FILE_NAME.yml'>

```yml

models:
  - name: my_model
    config:
      contract:
        enforced: true
        alias_types: false  # true по умолчанию

```

</File>

## Размер, точность и масштаб {#size-precision-and-scale}

Когда dbt сравнивает типы данных, он не будет сравнивать такие детальные характеристики, как размер, точность или масштаб. Мы считаем, что вам не стоит беспокоиться о разнице между `varchar(256)` и `varchar(257)`, так как это не сильно влияет на опыт пользователей, выполняющих запросы далее по цепочке. Вы можете добиться более точного утверждения, [написав или используя пользовательский тест](/best-practices/writing-custom-generic-tests).

Обратите внимание: необходимо указать размер varchar или масштаб числового типа, иначе dbt использует значения по умолчанию. Например, если тип `numeric` по умолчанию имеет точность 38 и масштаб 0, то числовой столбец хранит 0 цифр после десятичного разделителя (то есть только целые числа), что может привести к ошибке при проверке соблюдения контракта. Чтобы избежать такого неявного приведения типов, укажите в `data_type` ненулевой масштаб, например `numeric(38, 6)`. <Constant name="dbt" /> версии 1.7 и выше выводит предупреждение, если при указании числового типа данных вы не задаёте точность и масштаб.

### Примеры {#examples}

<File name='models/dim_customers.yml'>

```yml
models:
  - name: dim_customers
    config:
      materialized: table
      contract:
        enforced: true
    columns:
      - name: customer_id
        data_type: int
        constraints:
          - type: not_null
      - name: customer_name
        data_type: string
      - name: non_integer
        data_type: numeric(38,3)
```

</File>

Предположим, ваша модель определена как:

<File name='models/dim_customers.sql'>

```sql
select
  'abc123' as customer_id,
  'My Best Customer' as customer_name
```

</File>

Почему требуется, чтобы инкрементальные модели также устанавливали [`on_schema_change`](/docs/build/incremental-models#what-if-the-columns-of-my-incremental-model-change), и почему `append_new_columns`?

Почему для инкрементальных моделей требуется также указывать [`on_schema_change`](/docs/build/incremental-models#what-if-the-columns-of-my-incremental-model-change), и почему именно `append_new_columns` или `fail`?

Представьте:
- Вы добавляете новый столбец и в SQL, и в спецификацию YAML
- Вы не задаёте `on_schema_change` или задаёте `on_schema_change: 'ignore'`
- dbt фактически не добавляет этот новый столбец в существующую таблицу — и операция upsert/merge по-прежнему выполняется успешно, поскольку она использует только уже существующие столбцы целевой таблицы (это давно установленное поведение)
- В результате возникает расхождение между контрактом, определённым в YAML, и фактической таблицей в базе данных — а значит, контракт теперь некорректен!

Почему `append_new_columns` (или `fail`), а не `sync_all_columns`? Потому что удаление существующих столбцов — это несовместимое изменение для моделей с контрактом! `sync_all_columns` работает как `append_new_columns`, но также удаляет столбцы, которые были удалены из модели, а для моделей с контрактом этого делать нельзя без перехода на новую версию.

## Устранение неполадок

<Expandable alt_header="Я получаю ошибку несоответствия контракту">
**Что пошло не так:** Если для модели включена проверка контракта, dbt проверяет, что набор данных, возвращаемый моделью, в точности соответствует значениям `name` и `data_type`, определённым в YAML для каждого столбца; при несоответствии dbt выдаёт ошибку.

**Решение:** Убедитесь, что `name`, `data_type` и количество столбцов в контракте соответствуют столбцам в определении модели. Подробнее см. в [документации по контрактам](/reference/resource-configs/contract).
</Expandable>

<Expandable alt_header="Новый столбец не появляется в моей инкрементальной модели">
**Что пошло не так:** Контракты для инкрементальных моделей поддерживаются, когда для `on_schema_change` задано значение `append_new_columns` или `fail`. Если вы добавляете новый столбец, но не задаёте `on_schema_change` (или задаёте значение `ignore`), dbt не добавляет этот столбец в существующую таблицу, что может привести к расхождению между контрактом, определённым в YAML, и фактической схемой таблицы.

**Решение:** Задайте `on_schema_change: append_new_columns` (или `fail`) для инкрементальных моделей с контрактом. Подробнее см. в разделе [Инкрементальные модели и `on_schema_change`](/docs/mesh/govern/model-contracts).
</Expandable>

<Expandable alt_header="Из таблицы моей инкрементальной модели исчез столбец">
**Что пошло не так:** `sync_all_columns` добавляет все новые столбцы в существующую таблицу и удаляет все столбцы, которые теперь отсутствуют, поэтому столбец может быть удалён из целевой таблицы, если его нет в новом запросе модели.

**Решение:** Для инкрементальных моделей с контрактом используйте `append_new_columns` (или `fail`), а не `sync_all_columns`. Удаление существующих столбцов — это несовместимое изменение для моделей с контрактом. Подробнее см. в разделе [Инкрементальные модели и `on_schema_change`](/docs/mesh/govern/model-contracts).
</Expandable>

<Expandable alt_header="Я получаю неожиданную ошибку несоответствия типов данных">
**Что пошло не так:** dbt применяет встроенное сопоставление псевдонимов типов к значениям `data_type` в YAML, а использование точности и масштаба по умолчанию (особенно для `numeric`) может привести к неявному преобразованию типов, из-за которого проверка контракта может завершиться ошибкой.

**Решение:** Чтобы отключить сопоставление псевдонимов типов, задайте `alias_types: false`. Чтобы избежать неявного преобразования числовых типов, укажите `data_type` с ненулевым масштабом (например, `numeric(38, 6)`). Подробнее см. в [документации по контрактам](/reference/resource-configs/contract).
</Expandable>

Допустимые значения ограничены `append_new_columns` и `fail`, потому что именно эти варианты считаются безопасными и предсказуемыми в контексте инкрементальных моделей:

- `append_new_columns` — dbt автоматически добавит новые столбцы в целевую таблицу, не затрагивая существующие данные. Это наиболее распространённый и относительно безопасный сценарий эволюции схемы.
- `fail` — dbt остановит выполнение с ошибкой, если схема изменилась. Это подходит для случаев, когда любые изменения схемы должны быть явно рассмотрены и обработаны вручную.

Другие варианты изменения схемы (например, удаление или переименование столбцов) могут привести к потере данных или нарушению логики инкрементальной загрузки, поэтому dbt не позволяет использовать их автоматически для инкрементальных моделей.

Почему `append_new_columns`, а не `sync_all_columns`? Потому что удаление существующих столбцов является критическим изменением для моделей с контрактами!

Почему используется `append_new_columns` (или `fail`), а не `sync_all_columns`? Потому что удаление существующих колонок является ломающим изменением (breaking change) для моделей с контрактом! `sync_all_columns` работает так же, как `append_new_columns`, но дополнительно удаляет удалённые колонки, а этого нельзя делать для моделей с контрактом, если только вы не повышаете версию.
