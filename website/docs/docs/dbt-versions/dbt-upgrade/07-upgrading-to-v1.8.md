## Что нужно знать перед обновлением {#what-to-know-before-upgrading}

dbt Labs стремится обеспечивать обратную совместимость для всех версий 1.x, за исключением изменений, явно указанных на этой странице. Если при обновлении вы столкнётесь с ошибкой, сообщите нам об этом, [создав issue](https://github.com/dbt-labs/dbt/issues/new).

## Треки релизов {#release-tracks}

<Constant name="dbt" /> предоставляет функциональность новых версий <Constant name="core" /> через [каналы выпуска](/docs/dbt-versions/dbt-release-tracks) с автоматическими обновлениями. Выберите канал выпуска в своих [средах](/docs/deploy/deploy-environments) разработки, тестирования и промышленной эксплуатации, чтобы получить доступ ко всем возможностям <Constant name="dbt" /> v1.8+ и не только. Чтобы обновить среду через [Admin API <Constant name="dbt" />](/docs/dbt-apis/admin-api) или [Terraform](https://registry.terraform.io/providers/dbt-labs/dbtcloud/latest), задайте для `dbt_version` строковое значение `latest`.

### Модульные тесты {#unit-tests}

Исторически, тестовое покрытие dbt ограничивалось [“данными” тестами](/docs/build/data-tests), оценивающими качество входных данных или структуру результирующих наборов данных.

В версии v1.8 мы вводим нативную поддержку [модульного тестирования](/docs/build/unit-tests). Модульные тесты проверяют вашу SQL-логику моделирования на небольшом наборе статических входных данных __до__ того, как вы материализуете вашу полную модель в производстве. Они поддерживают подход разработки, основанный на тестировании, улучшая как эффективность разработчиков, так и надежность кода.

Начиная с версии v1.8, когда вы выполняете команду `dbt test`, она будет запускать как модульные, так и данные тесты. Используйте метод [`test_type`](/reference/node-selection/methods#the-test_type), чтобы запускать только модульные или данные тесты:

```shell
dbt test --select "test_type:unit"           # запустить все модульные тесты
dbt test --select "test_type:data"           # запустить все данные тесты
```

Модульные тесты определяются в YML-файлах в вашем каталоге `models/` и в настоящее время поддерживаются только для SQL-моделей. Чтобы различать их, конфигурация `tests:` была переименована в `data_tests:`. Оба варианта в настоящее время поддерживаются для обратной совместимости.

#### Новый синтаксис `data_tests:` {#new-data_tests-syntax}

Синтаксис `tests:` изменяется, чтобы отразить добавление модульных тестов. Начните миграцию вашего [теста данных](/docs/build/data-tests#new-data_tests-syntax) YML на использование `data_tests:` после обновления до версии v1.8, чтобы избежать проблем в будущем.

```yml
models:
  - name: orders
    columns:
      - name: order_id
        data_tests:
          - unique
          - not_null
```

#### Флаг `--empty` {#the-empty-flag}

Команды [`run`](/reference/commands/run#the-empty-flag) и [`build`](/reference/commands/build#the-empty-flag) теперь поддерживают флаг `--empty` для выполнения сухих прогонов только со схемой. Флаг `--empty` ограничивает ссылки и источники до нуля строк. dbt все равно выполнит SQL модели в целевом хранилище данных, но избежит дорогостоящих чтений входных данных. Это проверяет зависимости и гарантирует, что ваши модели будут правильно построены.

### dbt-core и адаптеры теперь независимы друг от друга

До версии v1.8 адаптеры dbt напрямую зависели от компонентов `dbt-core`, а `dbt-core` зависел от адаптера для выполнения операций. Эта двусторонняя зависимость затрудняла независимую разработку адаптеров. Начиная с <Constant name="dbt" /> v1.8, [`dbt-core` и адаптеры больше не зависят друг от друга](https://github.com/dbt-labs/dbt-adapters/discussions/87), что упрощает их независимое сопровождение и развитие.

Для обратной совместимости пакеты адаптеров по-прежнему зависят от `dbt-core` при установке. Для запуска проекта dbt по-прежнему требуются и `dbt-core`, и адаптер, и начиная с версии v1.0 многие пользователи устанавливают их вместе с помощью [`pip install dbt-<adapter>`](/docs/dbt-versions/dbt-upgrade/Older%20versions/upgrading-to-v1.0#installation).

Это поведение остается неизменным. Например, команда `pip install dbt-snowflake` устанавливает последние версии как `dbt-core`, так и `dbt-snowflake`.

### Устаревшая функциональность

Возможность для установленных пакетов переопределять встроенные материализации без явного согласия пользователя устаревает.

- Переопределение встроенной материализации из установленного пакета вызывает предупреждение об устаревании.
- Использование пользовательской материализации из установленного пакета не вызывает предупреждения об устаревании.
- Использование переопределения встроенной материализации из корневого проекта через оберточную материализацию все еще поддерживается. Например:

  ```sql
  {% materialization view, default %}
  {{ return(my_cool_package.materialization_view_default()) }}
  {% endmaterialization %}
  ```

### Управление изменениями в устаревших поведениях {#managing-changes-to-legacy-behaviors}

В <Constant name="dbt" /> v1.8 появились флаги для [управления изменениями устаревшего поведения](/reference/global-configs/behavior-changes). Вы можете включить недавно добавленные изменения (отключённые по умолчанию) или отключить устоявшиеся изменения (включённые по умолчанию), задав для соответствующих флагов в разделе `flags` файла `dbt_project.yml` значения `true` / `false` соответственно.

Вы можете прочитать больше о каждом из этих изменений поведения по следующим ссылкам:

- (Стабильная функция, включена по умолчанию) [Требовать явного переопределения встроенных материализаций пакетами](/reference/global-configs/behavior-flags/require_explicit_package_overrides_for_builtin_materializations)
- (Новая функция, отключена по умолчанию) [Требовать имена ресурсов без пробелов](/reference/global-configs/behavior-flags/require_resource_names_without_spaces)
- (Новая функция, отключена по умолчанию) [Выполнять хуки проекта (`on-run-*`) в команде `dbt source freshness`](/reference/global-configs/behavior-flags/source_freshness_run_project_hooks)

## Кратко о других изменениях

- Пользовательские значения по умолчанию для [флагов глобальной конфигурации](/reference/global-configs/about-global-configs) следует задавать в словаре `flags` в файле [`dbt_project.yml`](/reference/dbt_project.yml), а не в [`profiles.yml`](/docs/local/profiles.yml). Поддержка их настройки в `profiles.yml` объявлена устаревшей.
- Новый флаг CLI [`--resource-type`/`--exclude-resource-type`](/reference/global-configs/resource-type) позволяет включать и исключать ресурсы при выполнении команд dbt `build`, `run` и `clone`. 
- Для повышения производительности dbt теперь выполняет один (пакетный) запрос при определении `source freshness` по метаданным вместо отдельного запроса для каждого источника.
- Синтаксис `DBT_ENV_SECRET_` изменён на `DBT_ENV_SECRET`: завершающее подчёркивание больше не требуется.
- Флаг `--select` теперь корректно ограничивает содержимое `catalog.json` выбранными узлами во всех проектах независимо от их размера. В предыдущих версиях селекторы узлов игнорировались в проектах со 100 и более узлами, а при выборе более 100 узлов источники полностью исключались из `catalog.json`.

- Пользовательские значения по умолчанию для [глобальных конфигурационных флагов](/reference/global-configs/about-global-configs) следует устанавливать в словаре `flags` в [`dbt_project.yml`](/reference/dbt_project.yml), вместо [`profiles.yml`](/docs/local/profiles.yml). Поддержка `profiles.yml` устарела.
- Новый флаг CLI [`--resource-type`/`--exclude-resource-type`](/reference/global-configs/resource-type) для включения/исключения ресурсов из dbt `build`, `run` и `clone`.
- Для улучшения производительности dbt теперь выполняет один (пакетный) запрос при расчете `source freshness` через метаданные, вместо выполнения запроса для каждого источника.
- Синтаксис для `DBT_ENV_SECRET_` изменен на `DBT_ENV_SECRET` и больше не требует завершающего подчеркивания.
