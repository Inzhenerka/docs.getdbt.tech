## Об архитектуре dbt {#about-dbt-architecture}

Приложение <Constant name="dbt" /> состоит из двух типов компонентов: статических и динамических. Статические компоненты работают постоянно и обеспечивают высокую доступность функций <Constant name="dbt" />, таких как веб‑приложение <Constant name="dbt" />. В свою очередь, динамические компоненты создаются по мере необходимости для выполнения задач, например фоновых заданий или обработки запросов на использование <Constant name="studio_ide" />.

<Constant name="dbt" /> доступен в большинстве регионов мира как в [одноарендной](/docs/platform/about-platform/tenancy#single-tenant) (AWS, Azure, и GCP), так и в [многоарендной](/docs/platform/about-platform/tenancy#multi-tenant) конфигурации.  

<Constant name="dbt" /> использует PostgreSQL для своей серверной части, S3-совместимые системы объектного хранения для журналов и артефактов, а также решение для хранения данных Kubernetes для создания динамических, постоянных томов. 

Все данные, хранящиеся на серверах <Constant name="dbt" />, защищены с помощью шифрования AES‑256.

## Коммуникация {#communication}

<Constant name="dbt" /> может взаимодействовать с несколькими внешними сервисами, включая платформы данных, репозитории git, сервисы аутентификации и каталоги. Все взаимодействия осуществляются по HTTPS (попытки подключения по HTTP перенаправляются на HTTPS). <Constant name="dbt" /> шифрует данные при передаче с помощью криптографического протокола TLS 1.2. 

TLS (Transport Layer Security) 1.2 — это промышленный стандартный протокол для шифрования конфиденциальных данных при их передаче через публичный интернет (который не предоставляет встроенного шифрования).

Типичный сценарий, который может часто встречаться, — это сотрудник, работающий в общественном месте, таком как аэропорт или кафе. Пользователь может быть подключен к небезопасной публичной сети, предоставляемой учреждением, к которой подключены и многие другие. Что, если среди них есть злоумышленник, запускающий программу, способную "захватывать" сетевые пакеты и анализировать их по воздуху?

Когда пользователь получает доступ к <Constant name="dbt" /> и запускает модели, которые взаимодействуют с платформой данных, информация, передаваемая между его компьютером и сервисами, шифруется с использованием TLS 1.2.

Если этот пользователь выполняет команду, которая инициализирует взаимодействие между <Constant name="dbt" /> и хранилищем данных (или git-репозиторием, или сервисом аутентификации) через интернет, такое взаимодействие также шифруется. Это означает, что даже если злоумышленник технически может видеть трафик, проходящий по незащищённой сети, он не сможет прочитать или каким‑либо образом разобрать передаваемую информацию. Он не сможет подслушать или взломать данные каким бы то ни было способом. Вместо этого он увидит бессмысленный набор символов, который невозможно расшифровать.

Для более детальной информации о наших практиках безопасности прочитайте нашу [страницу безопасности](https://getdbt.com/security).

### Взаимодействие с хранилищем данных {#data-warehouse-interaction}

Основная роль <Constant name="dbt" /> заключается в обработке данных, а не в их хранении. Приложение <Constant name="dbt" /> позволяет пользователям отправлять SQL в хранилище данных для выполнения преобразований. Однако пользователи могут отправлять SQL, возвращающий данные клиентов в приложение <Constant name="dbt" />. Эти данные никогда не сохраняются и существуют только в памяти экземпляра на протяжении сеанса. Для надлежащей защиты данных клиентов необходимо настроить соответствующие разрешения <Term id="data-warehouse" />, чтобы предотвратить несанкционированный доступ к конфиденциальным данным или их хранение.


Некоторые поставщики хранилищ данных предлагают расширенные функции безопасности, которые можно использовать в <Constant name="dbt" />. [Частные подключения](/docs/platform/secure/private-connectivity/private-connectivity) позволяют поддерживаемым платформам данных на AWS взаимодействовать с <Constant name="dbt" /> без передачи трафика через общедоступный интернет. [Snowflake](/docs/platform/manage-access/set-up-snowflake-oauth) и [BigQuery](/docs/platform/manage-access/set-up-bigquery-oauth) предлагают интеграцию с Oauth, которая обеспечивает дополнительный уровень безопасности для платформ данных (только для тарифного плана Enterprise).

### Синхронизация с git {#git-sync}

<Constant name="dbt" /> может синхронизироваться с различными поставщиками git, включая [Github](/docs/platform/git/connect-github), [Gitlab](/docs/platform/git/connect-gitlab), и [Azure DevOps](/docs/platform/git/connect-azure-devops) в своей интегрированной среде разработки ([<Constant name="studio_ide" />](/docs/platform/studio-ide/develop-in-studio)). Взаимодействие осуществляется по HTTPS, а не по SSH, и защищено протоколом TLS 1.2 для данных при передаче.

Информация о git‑репозитории хранится на серверах <Constant name="dbt" />, чтобы быть доступной во время сессий <Constant name="studio_ide" />. Когда синхронизация с git отключена, необходимо [обратиться в службу поддержки](mailto:support@getdbt.com) с запросом на удаление синхронизированных данных.

### Сервисы аутентификации {#authentication-services}

Настройки <Constant name="dbt" /> по умолчанию позволяют использовать локальных пользователей с учетными данными, хранящимися в <Constant name="dbt" />. Однако в качестве альтернативы предлагаются интеграции с различными сервисами аутентификации, включая [сервисы единого входа](/docs/platform/manage-access/sso-overview). Доступ к функциям можно предоставлять/ограничивать по ролям с помощью [RBAC](/docs/platform/manage-access/about-user-access#role-based-access-control-).

Функции SSO являются важными, поскольку они сокращают количество учетных данных, которые пользователю необходимо поддерживать. Пользователь входит в систему один раз, и токен аутентификации используется совместно всеми интегрированными сервисами (такими как <Constant name="dbt" />). Этот токен имеет срок действия и должен обновляться через заданные интервалы времени, что требует повторного прохождения процесса аутентификации. Если пользователь отключен в сервисе‑провайдере SSO, его доступ к <Constant name="dbt" /> также отключается, и он не может обойти это ограничение с помощью локальных учетных данных.

[Snowflake](/docs/platform/manage-access/set-up-snowflake-oauth) и [BigQuery](/docs/platform/manage-access/set-up-bigquery-oauth) предлагают сервисы OAuth (JSON для передачи информации и вызовы API для аутентификации) в качестве альтернативы SAML (XML для передачи информации и файлы cookie сеанса для аутентификации). Пользователи могут проходить аутентификацию на платформе данных для безопасного доступа к <Constant name="dbt" /> и блокировки доступа при отзыве учетных данных.
