Чтобы улучшить преобразования данных и быстрее выпускать продукты на основе данных, вы можете запускать [задания слияния](/docs/deploy/merge-jobs) для реализации рабочего процесса непрерывного развёртывания (CD) в <Constant name="dbt" />. Задания слияния могут автоматически собирать изменённые модели при слиянии запроса на включение изменений (PR), обеспечивая применение последних изменений кода в рабочей среде. Вам не нужно ждать следующего запуска задания по расписанию, чтобы получить последние обновления.

<Lightbox src="/img/docs/dbt-platform/using-dbt-platform/cd-workflow.png" width="90%" title="Рабочий процесс непрерывного развёртывания в dbt"/>

Вы также можете внедрить непрерывную интеграцию (CI) в <Constant name="dbt" />, что позволит дополнительно сократить время доставки изменений в рабочую среду и повысить качество кода. Подробнее см. в разделе [Непрерывная интеграция в <Constant name="dbt" />](/docs/deploy/continuous-integration).

## Запуск заданий с помощью автоматизации или API

[Задания слияния](/docs/deploy/merge-jobs) и [задания развёртывания](/docs/deploy/deploy-jobs) запускаются по событиям от вашего [провайдера <Constant name="git" />](/docs/platform/git/configure-git) или по другим триггерам, настроенным в <Constant name="dbt" />. Задания слияния, реагирующие на слияния, используют механизм вебхуков, кратко описанный ниже в разделе [Как работают задания слияния](/docs/deploy/merge-jobs) и подробно рассмотренный в разделе [Настройка запуска задания при слиянии в Git](/docs/deploy/merge-jobs).

Чтобы запустить то же задание слияния или развёртывания из собственных инструментов, используйте [Administrative API](/docs/dbt-apis/admin-api) и [Trigger Job Run](/dbt-cloud/api-v2#/operations/Trigger%20Job%20Run). Сначала настройте и проверьте задание в <Constant name="dbt" />, запишите идентификаторы учётной записи и задания из URL развёртывания или настроек задания, выполните аутентификацию с помощью [сервисных токенов](/docs/dbt-apis/service-tokens) или [персональных токенов доступа](/docs/dbt-apis/user-tokens), сформируйте заголовки HTTPS-запроса и тело JSON согласно описанию [Trigger Job Run](/dbt-cloud/api-v2#/operations/Trigger%20Job%20Run), а затем отслеживайте полученный запуск в истории заданий вместе с запусками, инициированными вебхуками.

- **Запуск CI через данные запроса Administrative API** отличается от повторного запуска заданий развёртывания или слияния. Следуйте инструкциям в разделе [Запуск задания CI с помощью API](/docs/deploy/ci-jobs#trigger-a-ci-job-with-the-api) на странице [Задания CI](/docs/deploy/ci-jobs).
- **Интеграции** с планировщиками и платформами (например, [Airflow и <Constant name="dbt" />](/guides/airflow-and-dbt-cloud), Prefect, Databricks) собраны на странице [Инструменты развёртывания](/docs/deploy/deployment-tools).

Когда вы настраиваете merge jobs, dbt Cloud отслеживает уведомления от вашего [Git-провайдера](/docs/platform/git/configure-git), указывающие на то, что PR был слит. Когда dbt Cloud получает одно из этих уведомлений, оно ставит в очередь новый запуск merge job.

Когда вы настраиваете задания слияния, <Constant name="dbt" /> ожидает уведомлений от вашего [провайдера <Constant name="git" />](/docs/platform/git/configure-git) о том, что PR был слит. Получив такое уведомление, <Constant name="dbt" /> ставит в очередь новый запуск задания слияния.

Вы можете настроить задания слияния для выполнения одного из следующих действий при слиянии PR:

| <div style={{width:'350px'}}>Команда для выполнения</div> | Описание использования |
| -------- | ----------------- |
| `dbt build --select state:modified+` | (По умолчанию) Сборка изменённых данных при каждом слиянии. <br /><br /><Constant name="dbt" /> собирает только изменённые модели данных и все зависящие от них объекты, как и в заданиях CI. Это помогает сократить затраты на вычисления и гарантирует, что последние изменения кода всегда попадают в рабочую среду. |
| `dbt compile` | Обновление применённого состояния для эффективных запусков заданий CI с минимальным объёмом работы. <br /><br /><Constant name="dbt" /> генерирует исполняемый SQL-код (из исходных файлов моделей, тестов и аналитических запросов), но не выполняет его. Это гарантирует, что изменения будут отражены в манифесте при следующем запуске задания CI, и позволяет отслеживать только актуальные изменения. |
