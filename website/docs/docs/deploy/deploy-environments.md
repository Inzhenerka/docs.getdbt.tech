Среды развертывания в <Constant name="dbt" /> необходимы для запуска заданий dbt в промышленной эксплуатации и использования функций или интеграций, зависящих от метаданных или результатов dbt. Среды определяют настройки, используемые при выполнении заданий dbt, в том числе:

- Версию <Constant name="dbt" />, которая будет использоваться для запуска вашего проекта
- Информацию о подключении к хранилищу данных (включая настройки целевой базы данных/схемы)
- [Профиль подключения](/docs/platform/about-profiles) (учетные данные, которые dbt использует для подключения)
- Версию вашего кода, которая будет выполняться
- Включен ли [dbt State](/docs/deploy/dbt-state-about) для среды — эту настройку могут наследовать задания в среде. Подробнее см. в разделе [Включение dbt State для сред и заданий](/docs/deploy/dbt-state-enable-env-jobs).

Проект <Constant name="dbt" /> может иметь несколько сред развертывания, что обеспечивает гибкость и позволяет настраивать выполнение заданий dbt под ваши задачи. Вы можете использовать среды развертывания, чтобы [создавать задания и настраивать их расписание](/docs/deploy/deploy-jobs#create-and-schedule-jobs), [включать непрерывную интеграцию](/docs/deploy/continuous-integration) и решать другие задачи в зависимости от ваших конкретных потребностей или требований.

:::tip Узнайте, как управлять средами <Constant name="dbt" />
Чтобы узнать о различных подходах к управлению средами <Constant name="dbt" /> и рекомендациях с учетом уникальных потребностей вашей организации, прочитайте [Рекомендации по работе со средами <Constant name="dbt" />](/guides/set-up-ci).
:::

Подробнее о различиях между средами разработки и развертывания см. в разделе [Среды <Constant name="dbt" />](/docs/dbt-platform-environments).

Существует три типа сред развертывания:
- **Производственная**: Среда для преобразования данных и построения конвейеров для производственного использования.
- **Промежуточная**: Среда для работы с производственными инструментами с ограничением доступа к производственным данным.
- **Общая**: Среда общего назначения для разработки развертывания.

Мы настоятельно рекомендуем использовать тип среды `Производственная` для окончательных, достоверных данных развертывания. Может быть только одна среда, отмеченная для окончательных производственных рабочих процессов, и мы не рекомендуем использовать `Общую` среду для этой цели.

## Создание среды развертывания {#create-a-deployment-environment}

Чтобы создать новую среду развертывания <Constant name="dbt" />, перейдите в **Orchestration** > **Environments**, затем нажмите **Create Environment**. Выберите **Deployment** в качестве типа среды. Этот вариант будет недоступен, если у вас уже есть среда разработки.

### Установить как производственную среду {#set-as-production-environment}

В <Constant name="dbt" /> для каждого проекта можно назначить одну среду развертывания, которая будет служить его производственной средой. Эта производственная среда _необходима_ для использования таких функций, как <Constant name="catalog" /> и ссылки между проектами. Она выступает источником достоверной информации о производственном состоянии проекта в <Constant name="dbt" />.

### Семантический слой {#semantic-layer}

Для клиентов, использующих <Constant name="semantic_layer" />, следующий раздел настроек окружения посвящён конфигурациям <Constant name="semantic_layer" />. В руководстве по настройке [The <Constant name="semantic_layer" /> setup guide](/docs/use-dbt-semantic-layer/setup-sl) приведены самые актуальные инструкции по установке и настройке.

Вы также можете использовать планировщик задач dbt для [проверки ваших семантических узлов в задаче CI](/docs/deploy/ci-jobs#semantic-validations-in-ci), чтобы убедиться, что изменения в коде dbt моделей не нарушают эти метрики.

### dbt State

[dbt State](/docs/deploy/dbt-state-about) сокращает количество ненужных повторных сборок узлов, повторно используя узлы, если ни логика, ни данные не изменились. Вы можете включить эту функцию для среды развертывания, чтобы задания в этой среде могли наследовать эту настройку. Этот параметр отображается только в том случае, если dbt State включен для вашей учетной записи. Инструкции см. в разделе [Включение dbt State для сред и заданий](/docs/deploy/dbt-state-enable-env-jobs).

## Промежуточная среда {#staging-environment}

Используйте промежуточную среду, чтобы предоставить разработчикам доступ к рабочим процессам и инструментам развертывания, контролируя при этом доступ к данным продуктивной среды. Промежуточные среды позволяют более детально управлять разрешениями, подключениями к хранилищу данных и изоляцией данных — в рамках одного проекта в <Constant name="dbt" />.

### Git-рабочий процесс {#git-workflow}

Есть несколько способов это сделать, но самый простой — настроить среду staging с помощью долгоживущей ветки (например, `staging`), аналогичной основной ветке (например, `main`), но отдельной от неё.

В этом сценарии рабочие процессы будут идеальным образом перемещаться вверх по потоку от среды разработки -> промежуточной среды -> производственной среды, с ветками разработчиков, питающимися в ветку `staging`, а затем в конечном итоге сливающимися в `main`. Во многих случаях ветки `main` и `staging` будут идентичны после слияния и останутся такими до следующей партии изменений из веток `development`, готовых к повышению. Мы рекомендуем устанавливать правила защиты веток на `staging`, аналогичные `main`.

Некоторые клиенты предпочитают подключать разработку и промежуточную среду к своей ветке `main`, а затем регулярно создавать ветки релизов (ежедневно или еженедельно), которые питаются в производственную среду.

### Зачем использовать промежуточную среду {#why-use-a-staging-environment}

Основные причины использования промежуточной среды (staging):
1. Дополнительный уровень проверки перед развертыванием изменений в рабочей среде. В промежуточной среде можно развертывать, тестировать и исследовать модели dbt.
2. Четкое разделение процессов разработки и данных рабочей среды. Это позволяет разработчикам использовать метаданные и такие возможности, как отложенное разрешение ссылок (deferral) и межпроектные ссылки, без доступа к данным в рабочих развертываниях.
3. Возможность для разработчиков создавать, редактировать и запускать задания по мере необходимости в промежуточной среде, сохраняя при этом ограничения доступа к рабочей среде с помощью [разрешений на уровне среды](/docs/platform/manage-access/environment-permissions).

**Условная конфигурация источников** позволяет вам указывать на "prod" или "non-prod" исходные данные в зависимости от среды, в которой вы работаете. Например, этот источник будет указывать на `<DATABASE>.sensitive_source.table_with_pii`, где `<DATABASE>` динамически разрешается на основе переменной среды.

<File name="models/sources.yml">

```yaml
sources:
  - name: sensitive_source
    database: "{{ env_var('SENSITIVE_SOURCE_DATABASE') }}"
    tables:
      - name: table_with_pii
```

</File>

Существует ровно один источник (`sensitive_source`), и все downstream dbt модели выбирают из него как `{{ source('sensitive_source', 'table_with_pii') }}`. Код в вашем проекте и форма DAG остаются последовательными во всех средах. Настраивая это таким образом, а не дублируя источники, вы получаете некоторые важные преимущества.

**Межпроектные ссылки в dbt Mesh:** Допустим, у вас есть `Project B`, зависящий от `Project A`, и в моделях настроены межпроектные ссылки ref. Когда разработчики работают в IDE с `Project B`, межпроектные ссылки ref будут разрешаться в промежуточное окружение `Project A`, а не в продакшен. При запуске заданий в промежуточном окружении эти ссылки ref будут давать те же результаты. Только продакшен-окружение будет ссылаться на данные продакшена, обеспечивая изоляцию данных и доступа без необходимости создавать отдельные проекты.

**Ускорение разработки благодаря отложенному разрешению ссылок:** Если в `Project B` также настроено промежуточное окружение развертывания, то ссылки на несобранные вышестоящие модели<VersionBlock firstVersion="1.11"> и [пользовательские функции (UDF)](/docs/build/udfs)</VersionBlock> внутри `Project B` будут разрешаться в это окружение с помощью [отложенного разрешения ссылок (deferral)](/docs/platform/about-defer), а не в модели<VersionBlock firstVersion="1.11"> и функции</VersionBlock> в продакшене. Это экономит время разработчиков и снижает затраты на хранилище данных, сохраняя при этом четкое разделение окружений.

Finally, the staging environment has its own view in [<Constant name="catalog" />](/docs/explore/explore-projects), giving you a full view of your prod and pre-prod data.

## Подключение для развертывания {#deployment-connection}

Для запуска заданий в среде развертывания необходимо настроить два параметра:

<SimpleTable>
| Параметр | Область действия | Что определяет |
| --- | --- | --- |
| **Подключение для развертывания** | Уровень среды | Где dbt создает объекты в вашем хранилище данных (база данных, схема и вычислительный ресурс) |
| **Профиль подключения** | Уровень проекта (назначается среде) | Как dbt проходит аутентификацию и какие учетные данные использует для подключения |
</SimpleTable>

Необходимо настроить оба параметра: одного подключения для развертывания недостаточно для запуска заданий. Также среде должен быть назначен [профиль подключения](#connection-profiles).

:::info Подключения для развертывания

Подключения для развертывания создаются и управляются на уровне аккаунта для аккаунтов <Constant name="dbt" /> и назначаются среде. Чтобы изменить тип хранилища данных, рекомендуем создать новую среду.

В каждом проекте может быть несколько подключений (аккаунт Snowflake, хост Redshift, проект Bigquery, хост Databricks и т. д.) одного и того же типа хранилища данных. Некоторые параметры такого подключения (базы данных, схемы и т. д.) можно переопределить в этом разделе настроек среды <Constant name="dbt" />.
:::

Эта секция определяет точное местоположение в вашем хранилище, на которое dbt должен нацелиться при создании объектов хранилища! Эта секция будет выглядеть немного по-разному в зависимости от вашего поставщика хранилища.

## Профили подключения {#connection-profiles}

Подключение для развертывания определяет, _где_ dbt создает объекты. Профиль подключения определяет, _как_ dbt проходит аутентификацию.

Учетные данные для развертывания управляются через профили подключения, которые создаются на уровне проекта и назначаются средам развертывания. Профили определяют учетные данные и атрибуты, которые dbt использует для подключения к вашему хранилищу данных.

Чтобы настроить учетные данные для этой среды, обратитесь к разделу [О профилях платформы dbt](/docs/platform/about-profiles). Для выполнения заданий среде должны быть назначены и подключение для развертывания, и профиль. В этом профиле можно настроить любые [расширенные атрибуты](/docs/dbt-platform-environments#extended-attributes).
