В <Constant name="dbt" /> доступны следующие типы заданий: 
- [Задания развертывания](/docs/deploy/deploy-jobs) &mdash; Создают ресурсы данных в производственной среде. Запускаются по расписанию, через API или после завершения другого задания.
- [Задания непрерывной интеграции (CI)](/docs/deploy/continuous-integration) &mdash; Тестируют и проверяют изменения кода перед слиянием. Запускаются при коммите в PR или через API.
- [Задания слияния](/docs/deploy/merge-jobs) &mdash; Развертывают объединенные изменения в производственной среде. Запускаются после успешного слияния PR или через API.
- [dbt State](/docs/deploy/dbt-state-about) &mdash; Повторно использует существующий узел, клонируя его или пропуская повторное построение, если логика и данные не изменились.

Следующая таблица сравнения описывает поведение различных типов задач:

|  | **Задания развертывания** | **Задания CI** | **Задания слияния** | **dbt State** |
| --- | --- | --- | --- | --- |
| Назначение | Создание ресурсов данных в производственной среде. | Сборка и тестирование нового кода перед слиянием изменений с кодом производственной среды. | Сборка изменений после слияния в производственной среде или обновление состояния для отложенного разрешения ссылок (deferral). | Повторное использование узла, если его логика и данные не изменились. Пересборка только в том случае, если результат будет отличаться. |
| Типы триггеров | Запуск по расписанию, через API или после успешного завершения другого задания. | Запуск при добавлении коммита в PR или через API. | Запуск после успешного слияния с веткой среды или через API.| Проверка при каждом запуске. Узел пропускается или клонируется, если его логика не изменилась, а давность данных вышестоящих узлов по-прежнему находится в пределах `lag_tolerance`. |
| Целевое расположение | Сборка в базе данных и схеме производственной среды. | Сборка в промежуточной базе данных и временной схеме, существующей в течение всего срока жизни PR. | Сборка в базе данных и схеме производственной среды. | Сборка в базе данных и схеме производственной среды. |
| Режим выполнения | Запуски выполняются последовательно, чтобы избежать конфликтов в базовом DAG. | Запуски выполняются параллельно для ускорения работы команды. | Запуски выполняются последовательно, чтобы избежать конфликтов в базовом DAG. | |
| Экономия за счет оптимизации запусков | Выявление заданий с избыточной частотой запуска и отмена ненужных запусков для предотвращения переполнения очереди. | Отмена текущих запусков при отправке более нового коммита, чтобы избежать избыточной работы. | Неприменимо | Пропуск пересборки или клонирование существующего узла, если логика и данные не изменились. |
| Сравнение состояний | Определение состояния требуется лишь иногда. | Почти всегда требуется сравнение состояния с производственной средой для сборки измененного кода и зависящих от него узлов. | Почти всегда требуется сравнение состояния с производственной средой для сборки измененного кода и зависящих от него узлов. | |
| Продолжительность запуска задания | Ограничение — 24 часа. | Ограничение — 24 часа. | Ограничение — 24 часа. | Ограничение — 24 часа. |
