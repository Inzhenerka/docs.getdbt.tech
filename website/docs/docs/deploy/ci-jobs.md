Вы можете настроить задания [непрерывной интеграции](/docs/deploy/continuous-integration) (CI) так, чтобы они запускались, когда кто-либо открывает новый pull request (PR) в вашем репозитории <Constant name="git" />. Запуская и тестируя только _измененные_ модели, <Constant name="dbt" /> обеспечивает максимально экономное использование ресурсов вашей платформы данных при выполнении этих заданий.

:::note Запуск CI-задач в монорепозиториях
Если у вас монорепозиторий с несколькими dbt‑проектами, открытие одного pull request в одном из проектов приведёт к запуску заданий для всех проектов, подключённых к этому монорепозиторию. Чтобы избежать этого, вы можете использовать отдельные целевые ветки для каждого проекта (например, `main-project-a`, `main-project-b`), чтобы разделить триггеры CI.
:::

## Предварительные требования
- У вас есть аккаунт <Constant name="dbt" />.
- Функции CI:
   - Для использования функций [параллельных проверок CI](/docs/deploy/continuous-integration#concurrent-ci-checks) и [автоматической отмены устаревших сборок](/docs/deploy/continuous-integration#smart-cancellation-of-stale-builds) ваш аккаунт <Constant name="dbt" /> должен использовать [тариф Starter, Enterprise или Enterprise+](https://www.getdbt.com/pricing/).
   - [Линтинг SQL](/docs/deploy/continuous-integration#sql-linting) доступен в [каналах обновлений <Constant name="dbt" />](/docs/dbt-versions/dbt-release-tracks) для аккаунтов <Constant name="dbt" /> на тарифах [Starter, Enterprise или Enterprise+](https://www.getdbt.com/pricing/). При добавлении SQLFluff в проект обратитесь к разделу [Настройка линтинга SQLFluff](/docs/deploy/continuous-integration#to-configure-sqlfluff-linting).

## Настройка CI-задач {#set-up-ci-jobs}

dbt Labs рекомендует создавать задание CI в отдельной [среде развертывания](/docs/deploy/deploy-environments#create-a-deployment-environment) <Constant name="dbt" />, подключенной к базе данных для промежуточного тестирования. Отдельная среда CI обеспечивает лучшую изоляцию временных схем CI от сборок в рабочей среде.

Вы можете запускать задания CI для пул-реквестов, направленных в ветку, отличную от `main`. Например, если вы используете долгоживущую ветку для промежуточного тестирования, вы можете связать с ней среду CI с помощью настроек [пользовательской ветки](/faqs/Environments/custom-branch-settings). Тогда задание в этой среде будет запускаться только при открытии пул-реквестов в эту ветку.

Подробнее см. в руководстве [Начало работы с тестами CI](/guides/set-up-ci).

Кроме того, иногда командам требуется, чтобы CI‑задания запускались при создании PR не только в ветку main. Если в рамках процесса релизов ваша команда поддерживает staging‑ветку, отдельное окружение позволит задать [пользовательскую ветку](/faqs/Environments/custom-branch-settings). Соответственно, CI‑задание в этом выделенном окружении будет запускаться только при создании PR в указанную пользовательскую ветку. Подробнее см. в разделе [Get started with CI tests](/guides/set-up-ci).

1. На странице среды развертывания нажмите **Создать задание** > **Задание непрерывной интеграции**, чтобы создать новое задание CI.

2. Параметры в разделе **Настройки задания**:
    - **Имя задания** &mdash; Укажите имя этого задания CI.
    - **Описание** &mdash; Добавьте описание задания CI.
    - **Среда** &mdash; По умолчанию выбрана среда, из которой вы создали задание CI. Чтобы изменить этот выбор, воспользуйтесь раскрывающимся списком.

3. Параметры в разделе **Триггер <Constant name="git" />**:
    - **Запуск по пул-реквестам** &mdash; По умолчанию включен. Задание будет запускаться каждый раз, когда разработчик открывает пул-реквест или отправляет коммит в существующий пул-реквест.
      - **Запуск для чернового пул-реквеста** &mdash; Включите этот параметр, если хотите также запускать задание каждый раз, когда разработчик открывает черновой пул-реквест или отправляет коммит в этот черновой пул-реквест.

4. Параметры в разделе **Настройки выполнения**:
    - **Команды** &mdash; По умолчанию здесь указана команда `dbt build --select state:modified+`. Она предписывает <Constant name="dbt" /> выполнять построение только новых или измененных моделей и зависящих от них нижестоящих объектов. Важно отметить, что сравнение состояний возможно только в том случае, если выбрана среда для отложенного разрешения ссылок (defer), с состоянием которой будет выполняться сравнение. Нажмите **Добавить команду**, чтобы добавить другие [команды](/docs/deploy/job-commands), которые должны вызываться при выполнении этого задания.
    - **Линтинг** &mdash; Включите этот параметр, чтобы dbt выполнял [линтинг SQL-файлов](/docs/deploy/continuous-integration#sql-linting) в вашем проекте в качестве первого шага `dbt run`. Если при этой проверке возникнет ошибка, dbt может либо **Остановить выполнение при ошибке**, либо **Продолжить выполнение при ошибке**. 
    - **dbt compare**<Lifecycle status="managed,managed_plus" /> &mdash; Включите этот параметр, чтобы сравнить последнее примененное состояние производственной среды (если оно существует) с последними изменениями из пул-реквеста и определить различия между ними. Чтобы включить сравнение на уровне записей и анализ первичного ключа, необходимо добавить [ограничение первичного ключа](/reference/resource-properties/constraints) или [тест на уникальность](/reference/resource-properties/data-tests#unique). В противном случае в <Constant name="dbt" /> появится сообщение об ошибке «Primary key missing» (отсутствует первичный ключ).
    
      Чтобы просмотреть отчет о сравнении, перейдите на [вкладку Compare](/docs/deploy/run-visibility#compare-tab) на странице сведений о запуске задания. Краткая сводка отчета также доступна в пул-реквесте у вашего провайдера <Constant name="git" /> (см. [пример отчета CI](#example-ci-check)).

      Чтобы просмотреть отчет о сравнении, перейдите на вкладку [Сравнение](/docs/deploy/run-visibility#compare-tab) в деталях выполнения задания. Краткое содержание отчета также доступно из pull запроса в вашем Git провайдере (см. [пример отчета CI](#example-ci-check)).

Кроме того, если вы зададите [`event_time`](/reference/resource-configs/event-time) в моделях/seeds/снимках/источниках, это позволит сравнивать совпадающие диапазоны дат в таблицах, отфильтровывая данные по пересекающимся диапазонам дат. Это полезно для ускорения рабочих процессов CI или настройки выборки данных.
      :::

    - **Сравнение изменений с окружением (Deferral)** &mdash; По умолчанию выбрано окружение **Production**, если вы его создали. Эта настройка позволяет <Constant name="dbt" /> сравнивать состояние кода в PR с кодом, выполняемым в окружении, используемом для deferral, чтобы проверять только изменённый код, а не строить всю таблицу или весь DAG.


      :::caution Манифесты для сравнения
      Последний успешный запуск в окружении может относиться к _любому_ заданию, которое обновляет в нём артефакты. Если выполняется много заданий с разными настройками, состояние, используемое для сравнения в CI, может меняться непредсказуемым образом. Даже при использовании deferral с окружением Production слияние или развёртывание, обновляющее манифест, пока открыты другие pull request, может привести к тому, что соответствующие запуски начнут включать не связанные с ними узлы `state:modified`, пока ветки не будут обновлены.
      :::

    - **Тайм-аут запуска** &mdash; Отменять задание CI, если время выполнения превышает заданный тайм-аут. Эта настройка помогает избежать чрезмерного потребления ресурсов хранилища данных при проверке CI. Если вы включите настройку **dbt compare**, значение тайм-аута по умолчанию составит `3600` (один час), чтобы предотвратить слишком длительное выполнение сравнений.
    - **dbt State** &mdash; [dbt State](/docs/deploy/dbt-state-about) повторно использует узлы, если их логика и данные не изменились, позволяя избежать ненужного перестроения. Выберите **On**, **Off** или **Inherited from environment**, чтобы включить или отключить эту функцию либо использовать настройку окружения. Эта настройка отображается только в том случае, если dbt State [включён](/docs/deploy/dbt-state-setup) в вашей учётной записи. Подробнее о [включении dbt State для отдельных заданий](/docs/deploy/dbt-state-enable-env-jobs#enabling-dbt-state-on-individual-jobs).

5. (Необязательно) Настройки в разделе **Расширенные настройки**: 
    - **Переменные окружения** &mdash; Задайте [переменные окружения](/docs/build/environment-variables), чтобы настроить поведение проекта при выполнении этого задания CI. Вы можете указать, что задание CI выполняется в окружении _Staging_ или _CI_, задав переменную окружения и изменив код проекта так, чтобы его поведение зависело от контекста. Команды часто обрабатывают только подмножество данных при запусках CI, используя переменные окружения для выбора логики в коде своего проекта dbt.
    - **Имя целевой конфигурации** &mdash; Задайте [имя целевой конфигурации](/docs/build/custom-target-names). Как и **Переменные окружения**, эта настройка позволяет изменять поведение проекта. С её помощью можно указать, что задание CI выполняется в окружении _Staging_ или _CI_, задав имя целевой конфигурации и изменив код проекта так, чтобы его поведение зависело от контекста. 
    - **Версия dbt** &mdash; По умолчанию [версия dbt](/docs/dbt-versions) наследуется из окружения. dbt Labs настоятельно рекомендует не менять настройку по умолчанию. Возможность изменить версию на уровне задания полезна только при обновлении проекта до следующей версии dbt; в остальных случаях несовпадение версий окружения и задания может привести к неожиданному поведению.
    - **Потоки** &mdash; По умолчанию используются 4 [потока](/docs/local/profiles.yml#%D0%BF%D0%BE%D1%82%D0%BE%D0%BA%D0%B8-%D0%B2%D1%8B%D0%BF%D0%BE%D0%BB%D0%BD%D0%B5%D0%BD%D0%B8%D1%8F). Увеличьте число потоков, чтобы выполнять больше моделей параллельно.
    <VersionBlock lastVersion="1.99">

    - **Создавать документацию при запуске** &mdash; Включите эту настройку, если хотите [создавать документацию проекта](/docs/explore/build-and-view-your-docs) при выполнении этого задания. По умолчанию она отключена, поскольку проверять создание документации при каждой проверке CI не рекомендуется.

    </VersionBlock>

    - **Проверять актуальность источников** &mdash; Включите эту настройку, чтобы выполнять команду `dbt source freshness` перед запуском этого задания CI. Подробнее см. в разделе [Актуальность источников](/docs/deploy/source-freshness).

## Запуск задания CI через API {#trigger-a-ci-job-with-the-api}

### Предварительные требования

- У вас есть учетная запись <Constant name="dbt" />.
- У вас есть [тарифный план Enterprise или Enterprise+](https://www.getdbt.com/pricing/) для <Constant name="dbt" />. Ранее оформленные тарифные планы Team также сохраняют доступ.
  - Для использования функций [Параллельные проверки CI](/docs/deploy/continuous-integration#concurrent-ci-checks) и [Интеллектуальная отмена устаревших сборок](/docs/deploy/continuous-integration#smart-cancellation-of-stale-builds) ваша учетная запись <Constant name="dbt" /> должна использовать [тарифный план Enterprise или Enterprise+](https://www.getdbt.com/pricing/) либо ранее оформленный тарифный план Team. На тарифных планах Starter эти функции недоступны при запуске задания CI через API.

1. Настройте задание CI через конечную точку API [Create Job](/dbt-cloud/api-v2#/operations/Create%20Job), указав `"job_type": ci`, или через [интерфейс <Constant name="dbt" />](#set-up-ci-jobs).
2. Вызовите конечную точку API [Trigger Job Run](/dbt-cloud/api-v2#/operations/Trigger%20Job%20Run), чтобы запустить задание CI. В тело запроса необходимо включить оба следующих поля:
   - Укажите идентификатор pull request (PR), используя одно из следующих полей:

      - `github_pull_request_id`
      - `gitlab_merge_request_id`
      - `azure_devops_pull_request_id`
- `non_native_pull_request_id` (например, Bitbucket)
   - Укажите `git_sha` или `git_branch`, чтобы запустить задание для нужного коммита или ветки.

## Семантические проверки в CI <Lifecycle status="self_service,managed,managed_plus" />

Автоматически тестируйте семантические узлы (метрики, семантические модели и сохранённые запросы) во время проверки кода, добавив в задание CI проверки с обращением к хранилищу данных. Это гарантирует, что изменения кода моделей dbt не нарушат работу этих метрик.

Для этого добавьте команду `dbt sl validate --select state:modified+` в CI задание. Это обеспечивает валидацию измененных семантических узлов и их зависимостей.

<Lightbox src="/img/docs/dbt-platform/deployment/sl-ci-job.png" width="90%" title="Семантические проверки в рабочем процессе CI" />

#### Преимущества
- Тестирование семантических узлов в задании CI поддерживает механизм deferral и выбор семантических узлов.
- Оно позволяет выявлять проблемы на ранних этапах разработки и предоставлять конечным пользователям высококачественные данные.
- При семантической проверке для семантических узлов в хранилище данных выполняется запрос EXPLAIN, чтобы убедиться, что сгенерированный SQL можно выполнить.
- Для семантических узлов и моделей, которые не зависят от изменённых моделей, <Constant name="dbt" /> использует модели из продакшена с помощью механизма deferral.

### Настройка семантических проверок в вашем CI задании {#set-up-semantic-validations-in-your-ci-job}
Чтобы узнать, как это настроить, обратитесь к следующим шагам:

1. Нажмите **Orchestration**.
2. Нажмите **Jobs**.
3. Выберите нужное задание.
4. Нажмите **Settings**.
5. Нажмите **Edit**.
6. Добавьте команду `dbt sl validate --select state:modified+` в поле **Commands** раздела **Execution settings**. Эта команда использует выборку по состоянию и механизм deferral для проверки всех семантических узлов, расположенных ниже по графу зависимостей от изменённых моделей. Чтобы сократить время выполнения задания, рекомендуем запускать CI только для изменённых семантических моделей.
7. Нажмите **Save**, чтобы сохранить изменения.

Существуют дополнительные команды и варианты использования, описанные в [следующем разделе](#use-cases), такие как валидация всех семантических узлов, валидация конкретных семантических узлов и так далее.

<Lightbox src="/img/docs/dbt-platform/deployment/ci-dbt-sl-validate-downstream.png" width="90%" title="Проверяйте семантические узлы, зависящие от изменённых моделей, в вашем задании CI." />

### Варианты использования {#use-cases}

Используйте или комбинируйте различные селекторы или команды для проверки семантических узлов в задании CI. Семантические проверки в CI поддерживают следующие сценарии использования:

<Expandable alt_header="Семантические узлы, зависящие от изменённых моделей (рекомендуется)">

Чтобы проверить семантические узлы, которые зависят от изменения модели, добавьте две команды в раздел **Настройки выполнения** вашего задания:

```bash
dbt build --select state:modified+
dbt sl validate --select state:modified+
```

- Первая команда строит измененные модели.
- Вторая команда проверяет семантические узлы, зависимые от измененных моделей.

Перед выполнением семантических проверок <Constant name="dbt" /> должен построить изменённые модели. Этот процесс гарантирует, что зависимые от них семантические узлы проверяются с использованием схемы CI через API семантического слоя dbt.

Для семантических узлов и моделей, которые не зависят от изменённых моделей, <Constant name="dbt" /> использует модели из производственной среды.

<Lightbox src="/img/docs/dbt-platform/deployment/ci-dbt-sl-validate-downstream.png" width="90%" title="Validate semantic nodes downstream of model changes in your CI job." />

</Expandable>

<Expandable alt_header="Семантические узлы, которые изменены или затронуты зависимыми измененными узлами.">

Чтобы проверять **только изменённые семантические узлы**, используйте следующую команду (с применением [state selection](/reference/node-selection/state-selection)):

```bash
dbt sl validate --select state:modified+
```

<Lightbox src="/img/docs/dbt-platform/deployment/ci-dbt-sl-validate-modified.png" width="90%" title="Используйте выборку на основе состояния для проверки изменённых моделей определения метрик в задании CI." />

Это проверит только семантические узлы. Он будет использовать отложенное состояние, настроенное в вашем оркестрационном задании, откладывая на ваши производственные модели.

</Expandable>

<Expandable alt_header="Выбор конкретных семантических узлов">

Используйте синтаксис селектора, чтобы выбрать _конкретный_ семантический узел(ы), который вы хотите проверить:

```bash
dbt sl validate --select metric:revenue
```

<Lightbox src="/img/docs/dbt-platform/deployment/ci-dbt-sl-validate-select.png" width="90%" title="Используйте выбор на основе состояния, чтобы проверять изменённые модели определения метрик в вашем задании CI." />

В этом примере CI задание проверит выбранный семантический узел `metric:revenue`. Чтобы выбрать несколько семантических узлов, используйте синтаксис селектора: `dbt sl validate --select metric:revenue metric:customers`.

Если вы не укажете селектор, <Constant name="dbt" /> проверит все семантические узлы в вашем проекте.

</Expandable>

<Expandable alt_header="Выбор всех семантических узлов">

Чтобы проверить _все_ семантические узлы в вашем проекте, добавьте следующую команду, чтобы отложить на вашу производственную схему при генерации запросов проверки хранилища:

   ```bash
   dbt sl validate
   ```

<Lightbox src="/img/docs/dbt-platform/deployment/ci-dbt-sl-validate-all.png" width="90%" title="Проверьте все семантические узлы в задании CI, добавив команду 'dbt sl validate' в настройки выполнения задания." />

</Expandable>

## Устранение неполадок {#troubleshooting}

<FAQ path="Troubleshooting/gitlab-webhook"/>

<DetailsToggle alt_header="CI выбирает модели, которых нет в моём pull request, или завершается на них с ошибкой">

Обычно это означает, что манифест для сравнения не соответствует коммитам вашей ветки. Другое задание перезаписало `manifest.json` с другими настройками, состояние Production (или другой среды, используемой для deferral) изменилось после слияния чужих изменений, пока ваш pull request оставался открытым, либо манифест ещё не обновился сразу после слияния. Встроенный механизм deferral использует в качестве цели среду, а не выбранный вручную ID задания.

Чтобы решить эту проблему, влейте последние изменения базовой ветки в ветку вашего pull request или выполните rebase на актуальную базовую ветку, чтобы включить недавние слияния. Чтобы обновить манифест для сравнения, не дожидаясь длительного развёртывания, используйте [задание слияния](/docs/deploy/merge-jobs) в той же среде, которую ваше задание CI использует для deferral. Например, задание, которое запускает `dbt parse --no-partial-parse` (или [`dbt compile`](/reference/commands/compile)) сразу после слияний.

</DetailsToggle>

<DetailsToggle alt_header="Задания CI иногда не запускаются при открытии PR через интеграцию с Azure DevOps (ADO)">

<Constant name="dbt" /> не запускает задание CI, если последний коммит в pull request или merge request уже вызвал запуск этого задания. Однако некоторые провайдеры (например, GitHub) учитывают результат существующего запуска для нескольких pull request или merge request.

Сценарии, в которых <Constant name="dbt" /> не запускает задание CI при использовании Azure DevOps:

1. Повторное использование ветки в новом PR
   - Если вы отмените предыдущий PR (PR 1), который вызвал запуск задания CI для слияния ветки (`feature-123`) с `main`, а затем откроете новый PR (PR 2) для слияния той же ветки с `main`, &mdash; <Constant name="dbt" /> не запустит новое задание CI для PR 2.

2. Повторное использование того же коммита
   - Если вы создадите новый PR (PR 2) с тем же коммитом (`#4818ceb`), что и в предыдущем PR (PR 1), который вызвал запуск задания CI, &mdash; <Constant name="dbt" /> не запустит новое задание CI для PR 2.

</DetailsToggle>

<DetailsToggle alt_header="Временные схемы не удаляются">
Если ваши временные схемы не удаляются после слияния или закрытия PR, это обычно указывает на одну из следующих проблем:
- Вы переопределили макрос <code>generate_schema_name</code>, и он не использует <code>dbt_cloud_pr_</code> в качестве префикса.

Чтобы решить эту проблему, измените ваш макрос так, чтобы имя временной схемы PR содержало требуемый префикс. Например:

- ✅ Имя временной схемы PR содержит префикс <code>dbt_cloud_pr_</code> (например, <code>dbt_cloud_pr_123_456_marketing</code>).
- ❌ Имя временной схемы PR не содержит префикс <code>dbt_cloud_pr_</code> (например, <code>marketing</code>).

Макрос создаёт схему, но ни одна модель dbt не записывает в неё данные. <Constant name="dbt" /> не удаляет временные схемы, в которые не записывались данные в результате выполнения модели dbt.

</DetailsToggle>

<DetailsToggle alt_header="Сообщения об ошибках, ссылающиеся на схемы из предыдущих PR">

Если вы получаете сообщение об ошибке, связанное со схемой, ссылающееся на <i>предыдущий</i> PR, это обычно указывает на то, что вы не используете производственное задание для вашего отложения и вместо этого используете <i>self</i>. Если предыдущий PR уже был объединен, схема предыдущего PR могла быть удалена к моменту запуска CI задания для текущего PR.

Чтобы исправить эту проблему, выберите производственное задание для отложения вместо self.

</DetailsToggle>

<DetailsToggle alt_header="Производственные задания не выполняются на этапе 'Клонирование Git репозитория'">

<Constant name="dbt" /> может выполнять checkout только для коммитов, принадлежащих исходному репозиторию. <Constant name="dbt" /> <i>не может</i> выполнять checkout для коммитов, принадлежащих форку этого репозитория.

Если при выполнении вашего job run на шаге **Clone <Constant name="git" /> Repository** вы получаете следующее сообщение об ошибке:

```
Сообщение об ошибке:
Клонирование в '/tmp/jobs/123456/target'...
Репозиторий успешно клонирован.
Переход на e845be54e6dc72342d5a8f814c8b3316ee220312...>
Не удалось перейти на указанную ревизию.
git checkout e845be54e6dc72342d5a8f814c8b3316ee220312
fatal: reference is not a tree: e845be54e6dc72342d5a8f814c8b3316ee220312
```

Дважды проверьте, что ваш PR не пытается объединиться, используя коммит, принадлежащий форку репозитория, прикрепленного к вашему проекту dbt.
</DetailsToggle>

<DetailsToggle alt_header="Задание CI не запускается у пользователей Virtual Private dbt">

Чтобы запускать задания в <Constant name="dbt" /> через [API](/docs/dbt-apis/admin-api), ваш Git-провайдер должен подключиться к вашей учетной записи <Constant name="dbt" />.

Если вы находитесь на плане Virtual Private dbt Enterprise, используя функции безопасности, такие как ingress PrivateLink или IP Allowlisting, регистрация CI хуков может быть недоступна и может привести к тихому сбою задания.
</DetailsToggle>

<DetailsToggle alt_header="Статус PR для CI задания остается 'в ожидании' в Azure DevOps после завершения выполнения задания">

Когда вы запускаете задание CI, статус пул-реквеста должен отображаться как `pending`, пока ожидается обновление от dbt. После завершения задания CI dbt отправляет статус в Azure DevOps (ADO), и он меняется на `succeeded` или `failed`.

Если статус не обновляется после выполнения задания, проверьте, не настроены ли политики веток Git, которые блокируют получение этих обновлений в ADO.

Одна из возможных причин — настройки **Reset conditions** в разделе **Status checks** политики ветки репозитория ADO. Если установить флажок **Reset status whenever there are new changes** (в разделе **Reset conditions**), это может помешать dbt передавать в ADO статус выполнения вашего задания CI.

Дополнительную информацию можно найти здесь:
- [Проверки статуса в Azure DevOps Services](https://learn.microsoft.com/en-us/azure/devops/repos/git/branch-policies?view=azure-devops&tabs=browser#status-checks)
- [Пул-реквест в Azure DevOps Services завис в ожидании обновления статуса](https://support.hashicorp.com/hc/en-us/articles/18670331556627-Azure-DevOps-Services-Pull-Request-Stuck-Waiting-on-Status-Update-from-Terraform-Cloud-Enterprise-Run)
- [Статус пул-реквеста](https://learn.microsoft.com/en-us/azure/devops/repos/git/pull-request-status?view=azure-devops#pull-request-status)

</DetailsToggle>
