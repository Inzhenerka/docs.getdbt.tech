# Об оркестрации с учетом состояния <Lifecycle status="private_preview" />

<IntroText>

При каждом запуске job state-aware orchestration автоматически определяет, какие модели нужно собрать, обнаруживая изменения в коде или данных.

State-aware orchestration помогает экономить вычислительные ресурсы и сокращать время выполнения, потому что при запуске job она проверяет наличие новых записей и собирает только те модели, которые действительно изменятся.


<Lightbox src="/img/docs/deploy/sao.gif" title="Оркестрация с учетом состояния на базе dbt v2" />

Мы построили оркестрацию с учетом состояния в <Constant name="dbt" /> на четырех основных принципах:

- **Общее состояние в реальном времени:** Все задания записывают данные в общее состояние на уровне моделей в реальном времени, позволяя <Constant name="dbt" /> пересобирать только измененные модели независимо от того, в каких заданиях они собираются.
- **Очередь на уровне моделей:** Задания выстраиваются в очередь на уровне моделей, что позволяет избежать любых «коллизий» и предотвратить повторную сборку моделей, которые только что были обновлены другим заданием.
- **Поддержка работы с учетом и без учета состояния:** Вы можете формировать задания динамически (с учетом состояния) или явно (без учета состояния). Оба подхода обновляют общее состояние, обеспечивая синхронизацию всех изменений.
- **Разумные настройки по умолчанию:** Оркестрация с учетом состояния работает сразу после включения (без дополнительных настроек), а для более тонкого управления предусмотрен необязательный параметр конфигурации. Подробнее см. в разделе [расширенные настройки оркестрации с учетом состояния](/docs/deploy/state-aware-setup#advanced-configurations).

:::note
Оркестрация с учетом состояния не зависит от [статического анализа](/docs/build/about-static-analysis#principles-of-static-analysis) и работает, даже когда `static_analysis` отключен.
:::

## Оптимизация сборок с помощью state-aware orchestration {#optimizing-builds-with-state-aware-orchestration}

Оркестрация с учетом состояния использует отслеживание общего состояния, чтобы определять, какие модели нужно построить, выявляя изменения в коде или данных при каждом запуске задания. Она также поддерживает настраиваемые интервалы обновления и настройки свежести источников, поэтому <Constant name="dbt" /> перестраивает модели только тогда, когда это действительно необходимо.

Например, вы можете настроить проект так, чтобы <Constant name="dbt" /> пропускал перестроение модели `dim_wizards` (и ее родительских моделей), если они уже обновлялись за последние 4 часа, даже если само задание запускается чаще.

Без каких-либо дополнительных настроек оркестрация с учетом состояния в <Constant name="dbt" /> автоматически определяет необходимость построения моделей при изменении кода или появлении новых данных в источнике (или в вышестоящей модели в случае [dbt Mesh](/docs/mesh/about-mesh)).

**Примечание:** Если модель не проходит [тест данных](/docs/build/data-tests), оркестрация с учетом состояния перестраивает ее при последующих запусках, а не использует повторно из предыдущего состояния. Это гарантирует, что dbt повторно проверяет модели с нерешенными проблемами качества данных.

### Обработка параллельных заданий

:::caution Не поддерживается в dbt State
В dbt State обработка параллельных заданий работает иначе. Полный список различий в поведении приведен в разделе [Известные отличия от оркестрации с учетом состояния](/docs/deploy/dbt-state-migration#known-differences-from-state-aware-orchestration).
:::

Если два отдельных задания зависят от одной и той же нижестоящей модели (например, `model_ab`) и оба обнаруживают изменения в вышестоящих ресурсах (`updates_on = any`), модель `model_ab` может быть построена дважды &mdash; по одному разу для каждого задания. Однако если `model_ab` уже была построена и с тех пор ничего не изменилось, ни одно из заданий не будет ее перестраивать. Вместо этого оба задания повторно используют существующую версию.

При оркестрации с учетом состояния все задания читают и записывают данные в одно и то же общее состояние и строят модель только при изменении состояния кода или данных. Это означает, что каждое задание самостоятельно оценивает необходимость перестроения модели на основе ее скомпилированного кода и состояния вышестоящих данных.

Что происходит, когда задания выполняются одновременно:

- Если оба задания доходят до одной и той же модели в один и тот же момент, одно из них ожидает завершения другого. Это предотвращает конфликты в хранилище данных, когда два задания пытаются одновременно построить одну и ту же модель.
- После того как первое задание завершит построение модели, второе задание все равно проверяет, нужно ли ее перестраивать. Если появились новые данные или изменения кода, которые необходимо учесть, второе задание строит модель заново. Если изменений нет и построение модели дало бы тот же результат, второе задание повторно использует модель.

Чтобы избежать слишком частого построения в рамках задания даже при изменении состояния кода или данных, можно снизить частоту построения с помощью настройки `build_after`. Информацию об использовании `build_after` см. в разделах [Свежесть моделей](/reference/resource-configs/freshness) и [Расширенные настройки](/docs/deploy/state-aware-setup#advanced-configurations).

### Обработка удаленных таблиц {#handling-deleted-tables}

Оркестрация с учетом состояния обнаруживает удаление таблиц моделей в хранилище и перестраивает эти модели, даже если код и данные не изменились.

При удалении таблицы в хранилище:

- dbt выдает предупреждение об отсутствии ожидаемой таблицы.
- Соответствующая модель ставится в очередь на перестроение в ходе текущего запуска, даже если код и данные не изменились.

Такое поведение обеспечивает согласованность между состоянием dbt и фактическим состоянием хранилища. Оно также уменьшает необходимость вручную очищать кеш или отключать оркестрацию с учетом состояния, когда модели изменяются вне dbt.

## Эффективное тестирование в state-aware orchestration <Lifecycle status="private_beta" /> {#efficient-testing-in-state-aware-orchestration}

:::info Функция в закрытой бета-версии
Возможности оркестрации с учетом состояния в <Constant name="dbt_platform" /> доступны только в <Constant name="fusion" />. Свяжитесь с вашим менеджером по работе с клиентами, чтобы включить <Constant name="fusion" /> в вашей учетной записи.
:::

Качество данных может ухудшаться по двум причинам:

- Новые изменения в коде меняют определения или добавляют граничные случаи.
- Новые данные, например дубликаты или неожиданные значения, делают downstream‑метрики некорректными.

Запуск стандартных [data tests](/docs/build/data-tests) dbt (`unique`, `not_null`, `accepted_values`, `relationships`) при каждой сборке помогает выявлять ошибки в данных до того, как они повлияют на бизнес‑решения. Однако для этого часто требуется несколько тестов на каждую модель и выполнение тестов даже тогда, когда в них нет необходимости. Если ничего значимого не изменилось, повторные запуски тестов не повышают покрытие и лишь увеличивают стоимость.

Благодаря <Constant name="fusion" /> dbt понимает SQL-код на основе логического плана скомпилированного кода. Это позволяет dbt определять, когда тест необходимо запустить повторно, а когда можно повторно использовать предыдущий результат теста вышестоящей зависимости.

Эффективное тестирование в state-aware orchestration снижает затраты на хранилище данных за счёт исключения избыточных data tests и объединения нескольких тестов в один запуск. Эта функциональность включает две оптимизации:

В настоящее время эффективное тестирование доступно только в заданиях развертывания, но не в заданиях непрерывной интеграции (CI) или слияния.

### Поддерживаемые data tests {#supported-data-tests}

Следующие тесты могут быть переиспользованы при включённом Efficient testing:
- [`unique`](/reference/resource-properties/data-tests#unique)
- [`not_null`](/reference/resource-properties/data-tests#not_null)
- [`accepted_values`](/reference/resource-properties/data-tests#accepted_values)

### Включение Efficient testing {#enabling-efficient-testing}

Прежде чем включать эффективное тестирование, убедитесь, что вы настроили [`static_analysis`](/docs/build/about-static-analysis#configuring-static_analysis).

Чтобы включить Efficient testing:

1. В главном меню перейдите в **Orchestration** > **Jobs**. 
2. Выберите задание развертывания. Перейдите к настройкам задания и нажмите **Edit**. 
3. В разделе **Enable dbt v2 cost optimization features** раскройте **More options**.
4. Выберите **Efficient testing**. По умолчанию эта функция отключена.
5. Нажмите **Save**.

### Пример {#example}

В следующем запросе выполняется join таблиц `orders` и `customers`:

```sql
with

orders as (

    select * from {{ ref('orders') }}

),

customers as (

    select * from {{ ref('customers') }}

),

joined as (

    select
        customers.customer_id as customer_id,
        orders.order_id as order_id
    from customers
    left join orders
        on orders.customer_id = customers.customer_id

)

select * from joined
```

- Тест `not_null`: `left join` может привести к появлению null‑значений для клиентов без заказов. Даже если upstream‑тесты проверили `not_null(order_id)` в orders, join может создать null‑значения downstream. Поэтому dbt всегда должен запускать тест `not_null` для `order_id` в этом результате.

- Тест `unique`: если `orders.order_id` и `customers.customer_id` уникальны upstream, уникальность `order_id` сохраняется, и можно переиспользовать результат upstream‑теста.

### Ограничения

Ниже приведены важные моменты, которые следует учитывать при использовании Efficient testing в state-aware orchestration:

- **Агрегированные тесты не поддерживают пользовательские конфигурации**. Тесты, в которых используются следующие [custom config options](/reference/data-test-configs), будут выполняться отдельно, а не в составе агрегированного пакета:

  ```yaml
  config:
    fail_calc: <string>
    limit: <integer>
    severity: error | warn
    error_if: <string>
    warn_if: <string>
    store_failures: true | false
    where: <string>
  ```
  
 - **Efficient testing is available only in deploy jobs**. CI and merge jobs currently do not have the option to enable this feature.
